# Does the always-on program reach sequence 1 after Linux's commit? (milestone 1, run 2)

```
Question      After Linux's commit, does the always-on sleep program write power-chip 0x0201 = 01
              (its sequence 1, after sequence 0's gate polls of 0x23b71c090 / 0x23b71c360)?
Known         Decode: sequence 1 writes 0x0201 = 01, sequence 5 02, wake sequence 10 00; a
              power-button start leaves 04; self-resets leave it unchanged [evidence 2026-11-16
              run36-38 "Premise check"; 2026-11-17 "Observation round 4" table]. Run 1 (today):
              watchdog 2 armed at the commit, reset at the watchdog-1 time, 0x0201 = 04 after,
              before not read [2026-11-20-m1-engine-start.md].
Prior art     Nov 16 old driver: runs 27b, 32 read 04 -> 01 (gates passed); run 22 stuck on the
              two gates, watchdog 2 reset at 5 s [run36-38 README].
Outcomes      A  pre 04, post 01  -> sequence 1 ran: past the gates; sleep path entered; no wake
                 sequence (00) and no sequence 5 (02): powered down or stuck after, never woken.
              B  pre 04, post 04  -> sequence 1 never wrote: the program stops in sequence 0
                 without watchdog 2's 5 s reset (lead 4, gate records, first).
              C  post 00 or 02    -> a wake sequence (00) or sequence 5 (02) ran: a wake started.
              D  pre not 04       -> compare pre/post the same way; equal = nothing written.
Tell apart    0x0201 read on the test kernel just before the sleep and after the reset.
              Record [1]='q', [2..3]=0x800f, [4..7] 0x23d2b8028 just before 0x23d2c4000
              (macOS 0x1000000, R62).
Not covered   Where inside sequence 0 or after sequence 1 it stops.
Safety        As run 1: kernel ds29, wdt=150, boot-once, reads only.
Budget        0 builds, 1 run.
Result        B, with one caveat. Run 2026-11-20 02:25 (ds29, cand 0xffffe, probe_k=15): record
              44 71 0f 80 00 00 00 01 4c 00 = 'q', k=15: 0x23d2b8028 = 0x01000000 just before
              0x23d2c4000 (macOS's value, R62). Reset 178 s after the start, fault shadow 0x000800
              (watchdog only). 0x0201: 04 after. The pre-sleep read on the test kernel came back
              empty (the runner's nvmem read printed nothing there); stock Linux read 04 at 02:21,
              before the boot-once reboot, and a reboot leaves 0x0201 unchanged [evidence
              2026-11-17 Observation round 4]. So sequence 1 did not write 01.
              Side reads (stock, 02:29, after the reset): 0x23d2b8028 = 2, the same as a stock boot
              on 11-16 (snapshot 2): the boot overwrites it, so it cannot show how far the program
              got. Watchdog 2: compare 0x7270e00, control 0.
              Decode note: 0x23d2b8028 marks sequence i with bit 2i on entry, 2i+1 on exit
              (var/recfg/t8103-recfg-brief.txt line 7); 0x01000000 = sequence 12 entered, so the
              watchdog 2 arming read in run 1 is sequence 12's (before the commit). Sequence 0
              (AWAKE->AOP_DDR, after the commit) re-arms watchdog 2 itself; it would end in a 5 s
              reset if it stalled on a poll, and no run did.
              Raw: var/milestone1/runs.tsv row 2, var/milestone1/run2-m1q15.log,
              var/regmap/scan-m1-aonprog-after-run2/reads.txt.
```
