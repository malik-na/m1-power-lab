Project brief for a Linux kernel reader · 6 November 2026

M1 Power Lab: from 1.1 W toward 0.1 W

We are trying to make an Apple M1 laptop sleep properly under Linux, and we are asking for help from someone who knows kernel power management. No Apple Silicon knowledge is assumed. The Rosetta stone below maps each Apple term to the Linux or Arm concept it resembles.

The machine

2020 MacBook Air (J313), Apple M1 (t8103). An arm64 SoC with 4 performance and 4 efficiency cores, no EL3 firmware and no PSCI. It runs Omarchy, an Arch-based Linux, on kernel linux-aurora 7.2.11.

The goal

Cut idle and sleep power. Kernel, bootloader, drivers and firmware are all fair game. Idle is already down 44%.

Where it stands

Linux sleeps with s2idle at 0.44 W because the SoC stays powered. Real suspend-to-RAM needs Apple's power-off and wake sequence, which is undocumented.

Why a hypervisor

We run macOS as a guest under m1n1, an EL2 hypervisor, and log every register write while it goes to sleep. That trace becomes the checklist for a Linux suspend-to-RAM.

Rosetta stone

Apple terms, in Linux and Arm words

Each entry gives the Apple name, the nearest Linux or Arm analogue, and the difference that matters here. The analogies are approximate.

Power control

PMGR→genpd power domains

The SoC power-controller register block. Linux drives it through genpd domains (apple,pmgr-pwrstate), one register per domain.

PMP→SCP / SCMI firmware

A power-management firmware coprocessor. Think SCP, but with a proprietary mailbox protocol. macOS reports device states to it.

SMC→embedded controller (EC)

System management controller. Owns battery, thermal and power sensors and the sleep handshake, through 4-character keys such as MBSE.

AON→always-on domain

The part of the SoC that stays powered while everything else is off.

SPMI PMU→PMIC on an SPMI bus

The power-management IC. It also holds the RTC alarm we use as a wake source.

Coprocessors

RTKit→remoteproc + rpmsg

Apple's RTOS on each coprocessor, plus the mailbox protocol the main CPU uses to talk to it.

DCP→display remoteproc

Display coprocessor. Runs firmware behind a mailbox. The display driver sends it requests and waits for replies.

ANS→NVMe behind a coprocessor

The SSD controller. Firmware-managed, exposes NVMe.

AOP→sensor-hub MCU

Always-on processor for sensors and low-power wake.

SEP→TEE / secure element

Secure Enclave, a separate security core with its own firmware.

CPU, interrupts, errors

AIC→GIC

Apple interrupt controller. Device IRQs and IPIs.

No PSCI→enable-method = "spin-table"

No EL3 firmware exists. CPUs start from a spin-table, so there is no PSCI CPU_OFF, CPU_SUSPEND or SYSTEM_SUSPEND, and Linux cannot cpu_die a core.

CYC_OVRD WFI_MODE→idle-state depth

A per-core register field that picks what wfi does: clock-gate, retention, or power-down. Mode 2 is clock-gate only.

DPC error→a RAS error record

Error from the instruction-side error unit. Reported in an implementation-defined register and raised as an SError.

no ECV→FEAT_ECV missing (Armv8.6)

Without enhanced counter virtualization, m1n1 keeps its own 1 ms timer on every guest core.

Sleep states

s2idle→freeze / s2idle

CPUs in their deepest idle state, SoC stays powered. What Linux does on the M1 today.

S2R→mem / deep

DRAM in self-refresh, SoC power cut, resume through the reset vector. What macOS does.

Retention WFI vs power-down→retention vs powerdown cpuidle states

Retention keeps core state at reduced voltage. Power-down loses it and returns through reset.

Power-plane child→a device in the dpm list

macOS's device power tree. Sleep waits until every child acknowledges its power-state change, like dpm_suspend() waiting on async suspends.

Hypervisor and security

m1n1→bootloader + thin EL2 hypervisor

Asahi Linux's bootloader. It can also run macOS as a guest and trap and log its MMIO.

SPTM / TXM→like pKVM's EL2, or a TEE

Apple's newer kernel-security monitor, running above the macOS kernel. New on the M1 with macOS 27.

GXF / SPRR→lateral ELs + permission indirection

Apple's "guarded" exception levels beside EL1 and EL2, and registers that remap page permissions. SPTM depends on both.

FEAT_FGT / FEAT_NV2→fine-grained traps / nested virt

Armv8.6 and Armv8.4 features. Upstream m1n1 needs one of them to host SPTM. The M1 has neither.

Why sleep is stuck at 0.44 W

Linux freezes the CPUs. macOS turns the whole chip off.

What Linux does today

s2idle keeps every CPU in power-down for the whole sleep. The rest of the SoC stays powered: memory controllers, fabric and coprocessors. 45 of 63 powered genpd domains stayed on through a sleep. The remaining small knobs are worth about 30–60 mW idle and about 20 mW asleep combined.

What real sleep needs

Suspend-to-RAM means DRAM in self-refresh, the SoC powered off, and a reset into a resume stub. Linux on the M1 lacks three pieces: a wake source that survives SoC-off, CPU power-down and restart without PSCI, and Apple's register sequence on the way in and out.

The macOS trace route

Watch macOS fall asleep, one register write at a time

m1n1 runs macOS as a guest at EL1 and traps the MMIO ranges we choose. The hard part was getting a macOS that boots under it on the M1.

  1. 1

    Get macOS 13.5, the version m1n1 supports

    Dead end

    Its installer refused to run on the M1's macOS 27.0.1. A USB installer failed because Apple's servers now hand every installer only the newest firmware package (27.2). macOS 14.8.3 has the same problem.

  2. 2

    Pivot: run the existing macOS 27.0.1 under m1n1

    Done

    m1n1 became the boot loader of the macOS volume, with Permissive security set in Recovery.

  3. 3

    Wall: SPTM/TXM

    Upstream modes fail

    macOS 27 is the first macOS that runs SPTM on the M1. m1n1's nested mode needs FEAT_NV2 and its emulation mode traps ERET through FEAT_FGT. The M1 has neither. Run natively, SPTM reads an EL2 register at EL1, takes an UNDEF and spins.

  4. 4

    Patch m1n1 for the M1

    7 patches

    On the local branch m1power/m1-sptm-native:

    • Rewrite every ERET in the guest images into a hypervisor call, and emulate it there.
    • Virtualize the memory-controller lock region (the M1 has one CTRR region).
    • Pass the guest's AMX enable through to hardware. Fixed a panic after login.
    • Run Rosetta's 4K-page processes unshadowed.
    • Skip an error-handler hook the M1 does not have.
    • Hold back the E-cluster idle report to the PMP. Tested, did not help, kept because it is harmless.
    • Run guest cores with WFI_MODE 2. This fixed the DPC error.
  5. 5

    macOS 27.0.1 boots to the desktop as an m1n1 guest

    First, as far as we know

    A hardware watchdog armed before each start turns any hang into an automatic reboot.

  6. 6

    E-core DPC error at sleep

    Solved

    Caused by the hypervisor's 1 ms tick. Details below.

  7. 7

    Sleep waits forever in power-state callbacks

    Current wall

    macOS panics after its sleep watchdog expires. Details below.

Leading hypothesis

The display driver waits for a reply from the DCP, or for the DCP's power domain to report off, and that reply never arrives under the hypervisor. m1n1 sits in the interrupt and mailbox path. An analysis to pick the next experiment is running.

The ask

Questions for a kernel expert

Answer any subset, by number. Pointers to code, commits, mailing-list threads or "don't do that" are all useful.

Suspend-to-RAM without PSCI

  1. Q1What kernel machinery should suspend-to-RAM use on an arm64 SoC with no PSCI and no EL3 firmware?Our sketch: platform_suspend_ops (.valid, .enter), syscore_ops for SoC state, and .enter calling cpu_suspend() with a finisher that does the final PMGR/PMIC writes and wfi. Resume arrives as a reset at wherever the reset vector (RVBAR) points, and that stub must reach cpu_resume. Is that the right skeleton? Is there any in-tree precedent outside PSCI, and what state that PSCI firmware normally handles (EL2/VHE registers, caches, MMU-off entry) must we handle ourselves?Why we ask: this is the core of the Linux side, and we want a shape maintainers would accept.
  2. Q2How do we take secondary CPUs offline for suspend when cpu_die is impossible?Cores boot by spin-table, so there is no PSCI CPU_OFF, and the suspend path's freeze_secondary_cpus() needs hotplug. Our park-mode hotplug passes 100 cycles per core but keeps cores powered. Is a custom enable-method with its own cpu_ops (real cpu_die / cpu_kill that powers the core down through PMGR) the expected route? What are the pitfalls?Why we ask: S2R needs the secondaries out of the way, and the obvious path is blocked.
  3. Q3How should a wake source that survives SoC power-off be wired and reported?The RTC alarm lives in the PMIC on the SPMI bus. Our driver (m1power/s2r-pmu-rtc) already wakes the M1 from s2idle as a normal wakeup IRQ. After S2R, the wake arrives as a reset, not an interrupt. Is the right pattern enable_irq_wake()/dev_pm_set_wake_irq() for s2idle, plus reading the PMIC alarm status early in resume and calling pm_wakeup_event() or pm_system_wakeup()? Anything about wakeup-source accounting or rtcwake to watch for?Why we ask: without a wake source that survives SoC-off, S2R is just power-off.
  4. Q4How should an irqchip be restored after the SoC lost power?After S2R the AIC (Apple's GIC equivalent) starts from reset. Is syscore_ops on the irqchip driver the right hook, or a cpu_pm notifier as the GIC uses? Which state should be rebuilt from the irq descriptors, and which saved raw?Why we ask: we want to get the restore order right the first time.

Power domains and a stuck suspend

  1. Q5How should genpd order the SoC power-off, and how do we model a firmware coprocessor that must be told device states?PMGR domains are genpd providers. For S2R, most of the 45 domains that stay on during s2idle must go off in a late phase before the final commit write, while always-on domains and the DRAM path stay up. Separately, the PMP firmware expects reports of device power states. Is noirq-phase genpd power-off the right place, should always-on domains use GENPD_FLAG_ALWAYS_ON, and would you model "tell the PMP" as a genpd power notifier, a parent domain, or something else?Why we ask: we want the domain model settled before writing the sequence.
  2. Q6How do you find the one device or domain that never acknowledges during a stuck suspend?In Linux we would reach for CONFIG_DPM_WATCHDOG, pm_debug_messages, initcall_debug and pm_print_times. macOS gives us a panic that names no driver and no thread. From EL2 we can read guest memory and every vCPU's registers, and log MMIO. What is your method in Linux, and what would you look for in an opaque guest: which device's MMIO went quiet, which domain states differ from a good sleep, or something else?Why we ask: this is exactly where we are stuck today.

Hypervisor

  1. Q7What is best practice for virtualizing an interrupt controller and mailbox doorbells so a guest's coprocessor replies are not lost?m1n1 sits in the interrupt and mailbox path between macOS and its coprocessors. A DCP reply arrives as a mailbox interrupt. What are the known ways an EL2 trap layer loses or delays a reply: ack ordering, not re-checking status after unmask, edge vs level, injecting while the vCPU sits in wfi? Which KVM vGIC lessons carry over?Why we ask: our leading hypothesis is a DCP reply that never arrives.
  2. Q8How do you debug a guest that waits forever for a device interrupt, from EL2?Mid-sleep snapshots show all eight cores in the normal idle loop, so the guest is waiting, not spinning. What would you log: per-IRQ pending vs masked state in the AIC, mailbox FIFO levels, the guest's DAIF at each wfi? Is there a standard way to catch an IRQ that is pending but masked, or delivered to a core that never took it?Why we ask: we want the next trace to settle the hypothesis in one run.
  3. Q9Is a 1 ms EL2 timer tick on every guest core a known source of trouble with core retention states? What is a better design?The M1 lacks FEAT_ECV, so m1n1 runs its own timer every 1 ms on every guest core. Idle cores left retention about 1000 times a second, and that triggered the DPC error. Forcing clock-gate-only WFI fixed it. Is this a known hazard on other arm64 parts? Would per-core deadline timers armed only when needed, or a tickless hypervisor that relies on the guest's own timer, be the right fix?Why we ask: clock-gate-only idle makes the guest unlike real hardware, which may hide or create sleep bugs.

CPU idle

  1. Q10Is there a safe way to use the deepest per-core power-down state from Linux on a spin-table platform?Per-core power-down loses all core state and comes back through reset, like a PSCI powerdown state, but nothing below Linux saves or restores it. Is cpu_suspend() plus cpu_pm notifiers enough for a cpuidle driver here? What about the per-core timer during power-down (a broadcast timer?), and pointing each core's reset vector at cpu_resume?Why we ask: the same mechanism would serve both runtime idle and S2R.

Small idle levers

  1. Q11Is there an upstream pattern for PCIe L1 substates at runtime but off around a device's D3 entry?L1.1/L1.2 on the Wi-Fi link save about 204 mW idle and about 180 mW asleep. With them on, brcmfmac (BCM4378) timed out entering D3 during suspend and the kernel aborted the suspend. We now drop the substates around suspend from user space. Would a PCI quirk, pci_disable_link_state() in the driver's suspend path, or a firmware-side fix be the accepted approach? Related: NetworkManager reset Wi-Fi power save after every resume until we added a drop-in. Where should that setting live?Why we ask: it works today, but only as a user-space workaround.
  2. Q12What is the accepted way to let an idle USB-C port controller sleep?One USB-C port controller never sleeps. A neighbouring project has an unmerged patch that puts idle port controllers to sleep. Unbinding the second USB-C controller saved only about 5 mW and powered off no domain. What runtime-PM pattern lets a Type-C port controller and its USB controller suspend with nothing plugged in, while still catching a plug event?Why we ask: we would rather follow an upstream pattern than carry the out-of-tree patch.
