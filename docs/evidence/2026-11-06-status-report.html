M1 Power Lab: from 1.1 W toward 0.1 W

The goal is to make a 2020 MacBook Air (M1, J313) running Omarchy Linux draw as little power as possible. Kernel, bootloader, drivers and firmware are all fair game. macOS is not the benchmark. We use it only to learn how Apple puts this chip to sleep.

Why sleep is stuck at 0.44 W

Linux freezes the CPUs. macOS turns the whole chip off.

What Linux does today

s2idle parks every CPU in power-down for 100% of the sleep. The rest of the system-on-chip stays powered: memory controllers, fabric and coprocessors. 45 of 63 powered SoC domains stayed on through a sleep. Knob tweaks cannot fix that. The ranked lever review put all the remaining small levers together at about 30–60 mW idle and about 20 mW asleep.

What real sleep needs

Suspend-to-RAM means DRAM in self-refresh, the SoC powered off, and the chip woken by a reset into a resume stub. Linux on the M1 lacks three pieces: a wake source that survives SoC-off, CPU power-down and restart, and the exact register sequence Apple uses on the way in and out.

The macOS trace route, today

Watch macOS fall asleep, one register write at a time

The plan is to run macOS as a guest under m1n1, Asahi's bootloader and hypervisor. m1n1 traps and logs every hardware access while macOS goes to sleep. Today was mostly about getting a macOS that would boot under it.

  1. 1

    Install macOS 13.5 on its own volume

    Dead end

    13.5 is the version m1n1's hypervisor supports on M1. Its installer app refused to run on the M1's macOS 27.0.1.

  2. 2

    USB installer: "Failed to download required installer asset (SFR)"

    Dead end

    It failed repeatedly. Apple's update server now gives every installer only the newest firmware package (27.2), even though Apple still signs 13.5. Firmware never goes backwards. macOS 14.8.3 has the same problem.

  3. 3

    Pivot: run the existing macOS 27.0.1 under m1n1

    Done

    m1n1 became the boot loader of Macintosh HD, with Permissive security set in Recovery. It took three Recovery attempts, because Recovery pairs with the default OS.

  4. 4

    New wall: SPTM/TXM

    Upstream modes fail

    macOS 27 is the first macOS that uses Apple's newer kernel security layer on the M1. Neither of m1n1's SPTM modes works there. Nested mode needs a CPU feature (FEAT_NV2) the M1 lacks. Emulation mode traps ERET through FEAT_FGT, which the M1 also lacks. Running natively hangs without a word, because SPTM reads an EL2 register and spins.

  5. 5

    Patch m1n1 for the M1

    5 fixes

    On the local branch m1power/m1-sptm-native:

    • Rewrite every ERET in the guest images into a call into m1n1, and emulate it there.
    • Virtualize the M1's single memory-controller lock region.
    • Pass the guest's AMX enable through to hardware. This fixed a panic right after login.
    • Run 4K-page (Rosetta) processes unshadowed.
    • Skip an error-handler hook the M1 does not have.
  6. 6

    macOS 27.0.1 boots to the desktop as an m1n1 guest

    First, as far as we know

    The sleep tracer records the hardware traffic. A hardware watchdog armed before each start turns any hang into an automatic reboot.

  7. 7

    Sleep fails at core power-down

    Under investigation

    Three tries, all failing at the same stage. Details below.

What's blocking us

One idle efficiency core faults on the way down

In every attempt, macOS tells the SMC it is going to sleep. It power-cycles the keyboard/trackpad SPI domain a few times, then one idle E-core faults. The first try also showed NVMe, USB-C accessory power and the display powering down cleanly before the fault.

The hypervisor caught a hardware SError while the core sat in idle (retention mode). Resuming raised it again, so wake was impossible. The trace logged 284k events, and 90% of them were one register toggling 2,000 times a second.

SErrors went to macOS this time. Its own handler panicked with DPC err (UNKNOWN:multiple) on E-core. The fault is real hardware, not something the hypervisor made up. The trace was cut down to a small set of zones.

Current lead

The cores run with m1n1's idle and power settings, because m1n1 blocks macOS's writes to the core power registers. One example is ACC_CFG=0xd at boot. macOS 13 tolerated this. macOS 27's sleep entry may not. A multi-agent analysis of Apple's error handler and the three traces is running now.

Grey areas

Open questions

  • What is the "DPC" core error?And which register holds it.
  • Can macOS 27 sleep under any hypervisor on M1?Nobody has reported it.
  • Is there a 5-second AON watchdog?Aura hit one on the A18 Pro. Slow trapping trips it.
  • Does m1n1's USB link keep the chip on?On the A18 Pro, the PMU never powered off while the hypervisor's USB stayed up.
  • Panel on costs 3.2 W, not ~1.9 WThe extra ~1.3 W is not identified yet.
  • Does PS-Poll really save anything?Pooled about −17 mW. Weak evidence.
  • CPU power-down vs parkBlocked on the installed m1n1 build (bc79acc4-dirty).
  • Is Apple's PMP firmware needed for Linux S2R?Or can Linux bypass it?

From the aurora-silicon survey

Useful leads from a neighbouring project

Nothing in that org runs macOS 27 under a hypervisor on M1, and nothing in it does suspend-to-RAM on M1. Still, a few pieces carry over:

  • Aura's 10-step macOS sleep sequence captured on the A18 Pro. It is a ready checklist for the M1.
  • tuxvdmtool reboots the M1 over USB-C with no button presses.
  • A Wi-Fi resume-wedge recovery script that reloads the driver after a bad resume.
  • Neural Engine runtime-PM numbers: 107–173 mW if the ANE is held on.
  • An unmerged kernel patch that puts idle USB-C port controllers to sleep.
Toolbox

What the lab runs on

m1power

On-device toolkit with knobs, a tune spec, a sleep ledger and a standby guard. Fixed today: a settle loop re-applies knobs until every one holds.

maclab

Remote lab that builds and boots kernels on the M1 and reboots back by a deadline if contact is lost. It once replayed a stale job overnight.

hv-trace-kit

m1n1 hypervisor tracer for the sleep path. It has async and unbuffered zones, a PMU post-mortem reader and a kernelcache unwrapper.

m1n1

Asahi's bootloader and hypervisor, on a locally patched branch for SPTM on the M1.

Hardware watchdog

Armed before each guest start, so a hang turns into a reboot.

Tailscale + Taildrop

SSH and file transfer between the bench and the Mac.

USB-C cable

Connects M3 Max and M1 Air for the m1n1 proxy and the trace stream.

Multi-agent research

Parallel reviewers and analysts. Models are matched to task difficulty.

Next steps

Short list

  1. Identify the E-core "DPC" error. Then test the lead by letting macOS 27 own the core power registers, starting with the boot-time write m1n1 blocks today.
  2. Keep the trace lean so the power-down stays fast, and drop m1n1's USB link at the sleep commit to rule out the A18 Pro failure modes.
  3. Set up tuxvdmtool so the bench can reboot the M1 without a hand on the power button.
  4. Decode the captured entry sequence and compare it with Aura's 10 steps and the static 13.5 sequence. That becomes the checklist for Linux suspend-to-RAM.
  5. Quick wins on the side: check whether the Neural Engine is held on, and find the extra 1.3 W with the panel on.
