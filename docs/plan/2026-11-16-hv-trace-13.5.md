# Plan: trace macOS 13.5's sleep entry under the m1n1 hypervisor (2026-11-16)

## Why

Linux suspend-to-RAM on the M1 Air now gets the chip's own sleep program through sequence 1
(0x0201 = 01), and then the machine is reset about 5 s after the release by firmware outside
the AP. Runs 36-38 ruled out watchdog 2 (moved to 100 s), the PMP (idled and acked), the
domains macOS turns off before its commit, and wake sources (all masked)
(`docs/evidence/2026-11-16-run36-38-restart/`). Under the earlier system firmware the same
program slept until the alarm, and the same program is byte-identical under 13.5, so the reset
comes from 13.5's coprocessor or power-chip firmware reacting to something Linux does or does
not do.

The 2026-11-07/08 traces (`tools/hv-trace-kit/runs/20261106/mac27/`, try55 and try62) were
taken on the earlier firmware, where Linux was not reset either. They show macOS's last
second before the commit: SMC `MBSE` slpw / `WKTP` 02 / slpa / AP power 0x201; PMP AP and IOP
power 0x201 with endpoint-0x20 notifications; AOP `0x00a4` to endpoints 0x20-0x28, then AP power
0x201; the power chip's 0x9f01 = 0x50 and the alarm block; one interrupt acknowledge on the
second power chip. Linux's driver matches that list. What we do not have is the same trace
under 13.5.

## Questions the trace answers

1. Does macOS 13.5 under the hypervisor sleep and wake on this M1 with 13.5 firmware, or is it
   reset ~5 s after its commit as Linux is? (If it is reset too, the hypervisor path itself is
   involved and the comparison must account for it.)
2. In the last 10 s before the commit, every message macOS sends to the SMC, PMP, AOP, DCP and
   now also the **SEP, SIO and NVMe (ANS)** coprocessors, every command on both power chips' SPMI
   controllers, and every PMGR/AON write, in order. Diffed against Linux run 36's entry.
3. If it wakes: the first AON/PMGR/SPMI accesses of the wake path (`S2R_SNAP_WAKE=1`).

## The one decision (Naeem)

m1n1 runs macOS under the hypervisor only when it is installed as the boot object of a macOS
volume with Permissive Security. After the 2026-11-14 reinstall the M1 has one macOS container
(nvme0n1p2, 100 GB) and the Omarchy stub (p3); system and OS firmware are 13.5.

| | A. The main macOS 13.5 volume | B. A new, separate 13.5 volume |
|---|---|---|
| Disk | nothing added | one APFS volume in the container (no partition change) |
| Time | ~30 min (1TR) | ~2.5 h (download, install, setup) + 1TR |
| Main macOS | boots m1n1 until Full Security is restored in 1TR (Stage E5) | untouched |
| Kernelcache | must match its build (check `sw_vers`; extract from Preboot if not 22G74) | installed from 22G74, matches `kc/kernelcache-13.5.macho` |

The runbook's original rule was "never change the main macOS's security"; option A breaks it
and is reversible in 1TR. Option B keeps it.

## What happens next with each outcome

- macOS 13.5 sleeps and wakes under the hypervisor: the diff of question 2 is the list of
  candidates; Linux runs then copy the differences (the run budget is Naeem's to set).
- macOS 13.5 is also reset ~5 s after its commit under the hypervisor: the reset is tied to
  running under m1n1 (the restart vector, the stage-1 loader or its boot policy), not to Linux;
  the next step is booting macOS 13.5 natively with only the power-chip bytes read before and
  after a sleep (no hypervisor).

## Option A chosen (Naeem, 2026-11-16): stage C on the main macOS volume

`m1n1.bin` built from `~/m1n1` bd6a43d4 (the project's hypervisor branch with the S2R wake
support used for the 11-07/08 traces), sha256 `063384e82c03d2148b068a3aeeeb75e55249c003651f9db343320b3f7ae4fc91`;
the proxy client is the same checkout. On the ESP it goes to `s2r/m1n1-bd6a43d.bin`.

1. **C0 (agent, over the cable, with Naeem's go). [DISK] one file:** copy `m1n1.bin` to
   `/boot/efi/s2r/m1n1-bd6a43d.bin`, check the sha256.
2. **Default to macOS (Naeem). [STARTUP DISK]:** Mac off; hold power until "Loading startup
   options..."; Option-click the macOS volume ("Macintosh HD") and choose **Always Use**. (1TR
   pairs with the default OS; bputil fails with a pairing error otherwise.)
3. **Enter 1TR (Naeem):** off again; hold power; **Options** → Continue; Utilities → Terminal.
4. **Read-only checks (Naeem, in the 1TR Terminal):**
   ```sh
   grep -A1 ProductBuildVersion "/Volumes/Macintosh HD/System/Library/CoreServices/SystemVersion.plist"   # want 22G74
   diskutil list                                   # the FAT "EFI - ..." partition, diskXsY
   diskutil mount diskXsY
   ls -l "/Volumes/<EFI name>/s2r/"                # m1n1-bd6a43d.bin listed
   ```
   If the build is not 22G74: stop there and tell the agent (the kernelcache must then come from
   this volume's Preboot, runbook B5).
5. **[SECURITY] (Naeem, in 1TR):**
   ```sh
   bputil -nkcas                                    # pick the macOS volume group; authenticate
   csrutil disable                                  # pick the same; authenticate
   kmutil configure-boot -c "/Volumes/<EFI name>/s2r/m1n1-bd6a43d.bin" --raw \
       --entry-point 2048 --lowest-virtual-address 0 -v "/Volumes/Macintosh HD"
   ```
   No `nvram boot-args`. Then Apple menu → Shut Down.
6. **Check (Naeem):** power on normally: Apple logo, then m1n1's console ending in
   "Running proxy..." on the Mac's screen. Leave it there for stage D, or hold power 10 s.
7. **Omarchy stays reachable** from the startup picker (hold power, pick it). The undo is
   runbook E5: in 1TR, `bputil -f` (Full Security) for the macOS volume, then Omarchy as
   default again (E2).

**C0 done 2026-11-16 13:35:** `/boot/efi/s2r/m1n1-bd6a43d.bin` on the ESP (nvme0n1p4, PARTUUID
`1dfcacf2-2e2b-487c-b2e6-7b5edaab9b89`), sha256 `063384e8…4fc91` matches the build. In 1TR the
